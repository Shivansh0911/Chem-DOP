# pI Predictor — Physics-Informed ML + LLM Peptide Design

Predicts the **isoelectric point (pI)** of amino acids and peptides, and then *designs* new
peptides to hit a pI you ask for in plain English.

Two ideas make it more than a calculator:

1. **The ML model corrects physics instead of replacing it.** Nine published pKa tables disagree with
   each other by up to ~1 pH unit. We compute all nine, then train models to predict the *residual* —
   how wrong the table was — against 8,435 experimental measurements. Result: **RMSE 0.489 vs 0.724
   for the best classical table (32% better)** on the same held-out set.
2. **The LLM proposes, the model disposes.** Groq's `gpt-oss-120b` turns a goal into a numeric spec
   and proposes candidate sequences; our ML model scores every one; the LLM reads the scores and
   refines. No number shown to the user is ever generated by the LLM.

---

## What is pI and why it matters

The **isoelectric point** is the pH at which a molecule carries zero net charge. It governs:

| Application | How pI is used |
|---|---|
| 2-D gel electrophoresis | First dimension separates proteins by pI (isoelectric focusing) |
| Ion-exchange chromatography | pI decides whether the molecule binds a cation or anion exchanger, and at what pH |
| Drug formulation | Therapeutic peptides are formulated away from pI, where solubility is lowest |
| Protein crystallisation | Minimum solubility at pI is exploited to precipitate protein |
| DNA/membrane binding | Highly basic peptides (high pI) bind negatively charged nucleic acids and membranes |

## The four features

| Tab | What it does |
|---|---|
| **Predict** | Sequence → pI, decomposed as `physics baseline + learned correction`, with a calibrated 90% interval, the titration curve, the three-model comparison, and all nine classical calculators plotted side by side. |
| **AI Designer** | "A 12-residue peptide that binds DNA and has a Trp for tracking" → numeric spec → 3 rounds of propose-and-score → final sequence. Every candidate is validated and re-scored; invalid ones are shown as rejected with the reason. |
| **pI Tuner** | Give a sequence and a target pI; get minimal point mutations (`K2E`) with a chemical rationale and the real predicted shift for each. |
| **How it works** | Live benchmark against all nine classical methods, feature importances, and the training facts. |

## How a prediction is actually made

```
sequence
   │
   ├─► 9 pKa tables (EMBOSS, IPC, Bjellqvist, Rodwell, …)
   │      each solves Henderson-Hasselbalch for net charge = 0
   │
   ├─► composition features (charged/aromatic/nonpolar fractions, per-residue
   │      fractions, absolute counts of D/E/C/Y/H/K/R, terminal residues,
   │      net charge at pH 7, spread across the nine tables)
   │
   ├─► RF / GB / Ridge predict the RESIDUAL (experimental pI − Rodwell pI)
   │
   ├─► applicability gate: outside the experimental window (physics pI 3.58–9.75)
   │      the correction fades to zero and the interval widens → pure physics
   │
   └─► pI = Rodwell physics + (faded) learned correction  ± conformal interval
```

**Why residual learning:** predicting pI from scratch means the model must re-learn chemistry it can
be told for free, and it collapses to the training range when shown an unusual sequence. Predicting
the *error* means physics carries the answer and extrapolates sensibly, while ML supplies the part
physics has no equation for (pKa shifts from neighbouring charges, termini, local environment).

**Why the interval is honest:** it is a split-conformal interval — the 90th percentile of absolute
error on held-out data (±0.571 pH units). On unseen sequences the truth lands inside it about 90%
of the time, by construction. It is not a standard deviation of tree votes dressed up as confidence.

## Results

Same 1,687 held-out sequences for every method. RMSE in pH units, lower is better.

| Method | RMSE | Type |
|---|---|---|
| **Random Forest (ours)** | **0.489** | physics + learned residual |
| Ridge (ours) | 0.506 | physics + learned residual |
| Gradient Boosting (ours) | 0.522 | physics + learned residual |
| Grimsley | 0.724 | classical pKa table |
| Rodwell | 0.768 | classical pKa table |
| Bjellqvist | 0.830 | classical pKa table |
| Sillero | 0.910 | classical pKa table |
| DTASelect | 0.924 | classical pKa table |
| EMBOSS | 0.929 | classical pKa table |
| Lehninger | 1.050 | classical pKa table |
| IPC | 1.052 | classical pKa table |
| Solomon | 1.056 | classical pKa table |

The app recomputes this table at training time, so the numbers on the "How it works" tab are always
the real ones for the deployed model — nothing is hardcoded.

## Dataset

Pérez-Riverol Y. et al., *Prediction of Isoelectric Point for Diverse Proteins Using Random Forest
and Gradient Boosting*, **Bioinformatics** 2016 — [github.com/bigbio/pIR](https://github.com/bigbio/pIR).

| File | Rows |
|---|---|
| `dataPeptidePIs.csv` | 7,391 |
| `dataProteinPIs.csv` | 1,066 |
| Combined after cleaning | **8,435** |

Measurements come from isoelectric focusing on pH 3–10 strips, which is exactly why the app refuses
to claim precision outside that window.

> **Note on the CSV columns.** The files also ship pre-computed calculator outputs (`bjell`, `expasy`, …).
> An earlier version of this project used them as features. That is a data leak in disguise: those
> columns don't exist for a sequence a user types, so at prediction time they were filled with zeros
> and every prediction collapsed toward the dataset mean — lysine and aspartic acid came out within
> 1 pH unit of each other. We now compute every calculator ourselves, with the same code at training
> and prediction time.

## Running locally

### Backend

```bash
cd backend
pip install -r requirements.txt
cp .env.example .env          # then put your Groq key in it
python model.py               # trains and saves models (~40 s)
uvicorn main:app --reload
```

API at `http://localhost:8000`, interactive docs at `/docs`.
Without a `GROQ_API_KEY` everything still works except the three AI features, which report that
they are disabled.

### Frontend

```bash
cd frontend
npm install
npm run dev
```

App at `http://localhost:5173`. No environment variable needed: Vite proxies the API paths to
`localhost:8000` in dev, and in production the frontend calls its own origin. Set `VITE_API_URL`
only when you want to point at some other backend.

## Deployment — one Render service

`render.yaml` deploys the **whole app as a single service**: Render builds the React app and FastAPI
serves it alongside the API. One URL, no CORS, no second host.

1. Push to GitHub.
2. Render → **New → Blueprint** → select the repo. It reads `render.yaml`.
3. In the service's **Environment** tab add `GROQ_API_KEY` (it is deliberately not in git).
4. Deploy. The build installs deps, builds the UI, and trains the models.

Notes on the free plan: the service sleeps after 15 minutes of inactivity and takes ~1 minute to wake,
and you get 750 instance-hours per month. Models are trained during the build, so a wake-up only
reloads them from disk. Open the page a few minutes before a demo.

<details>
<summary>Alternative: split hosting (Netlify frontend + Render backend)</summary>

Also supported. Deploy `backend/` as a Render service, deploy `frontend/` to Netlify with
`VITE_API_URL=https://<your-service>.onrender.com`. `frontend/public/_redirects` already handles
SPA routing. This is only worth it if you want Netlify's CDN — otherwise the single service is simpler.
</details>

## Limitations

- Trained on linear, unmodified sequences of the 20 standard residues. No disulfides, no
  phosphorylation or other PTMs, no non-standard residues.
- Reliable between physics pI 3.58 and 9.75; outside that the app says so and falls back to physics.
- Predictions are computational estimates and should be verified experimentally.
